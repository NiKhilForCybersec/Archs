AWS Security

AWS provides a comprehensive set of native security services following the shared responsibility model. Understanding these services and their integration is critical for securing cloud workloads on AWS.

IAM Deep Dive

IAM Policy Evaluation: How AWS Decides Allow/Deny
1
Request Context
Principal attempts an action on a resource
API Request
Principal: arn:aws:iam::123456789012:user/developer
Action: s3:GetObject  
Resource: arn:aws:s3:::prod-data-bucket/sensitive/report.pdf
Conditions: 
  - Source IP: 10.0.1.50
  - MFA: Not present
  - Time: 2024-01-15T14:30:00Z
2
Explicit Deny Check (SCPs, Identity, Resource)
Any explicit deny = request denied immediately
Service Control Policy (SCP)
// Organization SCP: Require MFA for sensitive buckets
{
  "Effect": "Deny",
  "Action": "s3:*",
  "Resource": "arn:aws:s3:::prod-data-bucket/sensitive/*",
  "Condition": {
    "BoolIfExists": {
      "aws:MultiFactorAuthPresent": "false"
    }
  }
}

Evaluation: MFA not present → EXPLICIT DENY
Result: REQUEST DENIED (SCP blocks before anything else)
3
If No Deny: Check for Allow
Must have explicit allow from identity AND resource policy
Policy Evaluation Order
1. SCPs (Organization-level guardrails)
   └─ Can only DENY, never grant permissions

2. Resource-based Policies (S3 bucket policy, KMS key policy)
   └─ Can allow cross-account access directly

3. Identity-based Policies (IAM user/role policies)
   └─ Permissions attached to the principal

4. Permissions Boundaries (if set)
   └─ Maximum permissions an identity can have

5. Session Policies (for assumed roles)
   └─ Further restricts role session

FINAL: All applicable policies must allow
       Any explicit deny wins
4
Example: Correct Configuration
User authenticates with MFA, request succeeds
Successful Request
Principal: arn:aws:iam::123456789012:user/developer
Action: s3:GetObject
MFA: Present ✓

SCP Check: MFA present → No deny
Bucket Policy: Allows account 123456789012 → Allow
IAM Policy: s3:GetObject on prod-data-bucket/* → Allow
Permissions Boundary: Allows S3 actions → Allow

Result: ACCESS GRANTED

Security Groups vs. NACLs

Feature Security Groups Network ACLs
Level Instance (ENI) level Subnet level
State Stateful (return traffic auto-allowed) Stateless (must allow both directions)
Rules Allow rules only Allow and Deny rules
Evaluation All rules evaluated together Rules processed in number order
Default Deny all inbound, allow all outbound Allow all (default NACL)
Use Case Primary instance firewall Subnet-level guardrails, block bad IPs

AWS Security Best Practices

AWS Security Implementation Guidelines

1. Use IAM Roles, Not Keys: EC2 instances, Lambda, ECS tasks should use IAM roles. Never embed access keys in code.

2. Enable GuardDuty Everywhere: Enable in all regions, all accounts. It's the foundation of AWS threat detection.

3. Centralize with Security Hub: Aggregate findings from GuardDuty, Inspector, Macie, Config. Single pane of glass.

4. SCPs for Guardrails: Use Service Control Policies to prevent dangerous actions org-wide (e.g., block root user, require encryption).

5. CloudTrail to S3 with Integrity: Enable CloudTrail in all regions, log to central S3 bucket with log file validation.

6. Encrypt Everything: S3 default encryption, EBS encryption, RDS encryption. Use KMS customer-managed keys for sensitive data.
