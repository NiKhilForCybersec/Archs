Patch Management

Unpatched systems are the #1 attack vector. Patch management is the disciplined process of acquiring, testing, and deploying patches to reduce vulnerability exposure. Speed matters—exploits often appear within days of patch release.

Patch Management Lifecycle

Patch Prioritization

Risk-Based Prioritization Model
# Patch Priority = CVSS + Exploitability + Asset Criticality + Exposure

Priority Factors:

1. CVSS Score (Base severity)
   Critical: 9.0-10.0  → Highest priority
   High:     7.0-8.9   → High priority
   Medium:   4.0-6.9   → Standard priority
   Low:      0.1-3.9   → Low priority

2. Exploitability (Is it being used?)
   Known exploited (CISA KEV)     → +3 priority
   Public exploit available       → +2 priority
   Proof of concept exists        → +1 priority
   No known exploit               → +0 priority

3. Asset Criticality (What does it affect?)
   Crown jewels (DC, ERP, PCI)    → +3 priority
   Production servers             → +2 priority
   Standard workstations          → +1 priority
   Non-production/test            → +0 priority

4. Exposure (Where is it?)
   Internet-facing                → +3 priority
   DMZ/semi-trusted               → +2 priority
   Internal network               → +1 priority
   Isolated/air-gapped            → +0 priority

Example:
  CVE-2024-XXXX on domain controller
  CVSS: 9.8 (Critical)      = Priority 4
  CISA KEV listed           = +3
  Domain Controller         = +3
  Internal (but critical)   = +1
  
  Total: 11 → EMERGENCY PATCH (24 hours)

Patching SLAs

Priority Criteria SLA Approval
Emergency Critical + actively exploited + internet-facing 24 hours CISO (emergency change)
Critical CVSS 9.0+ or CISA KEV listed 7 days Security team
High CVSS 7.0-8.9 14 days Standard change
Medium CVSS 4.0-6.9 30 days Standard change
Low CVSS 0.1-3.9 90 days Bundled with regular updates

Patch Automation

Automated Patching Workflow
1
Patch Tuesday (or vendor release)
Microsoft releases monthly patches
Trigger
Microsoft Patch Tuesday: 2nd Tuesday of month
Adobe, Oracle, etc.: Various schedules
Linux: Rolling updates (apt, yum)
Zero-days: Out-of-band emergency releases
2
Ring-Based Deployment
Phased rollout to limit blast radius
Deployment Rings
Ring 0: IT/Security test machines     (Day 1)
         → 10 devices, immediate deploy
         → Validate no breakage
         
Ring 1: IT department pilot           (Day 3)
         → 100 devices, early adopters
         → Monitor for issues
         
Ring 2: General population wave 1     (Day 7)
         → 30% of endpoints
         → Business validation
         
Ring 3: General population wave 2     (Day 10)
         → Remaining 70%
         → Full rollout

Ring 4: Servers (maintenance window)  (Day 14)
         → Production servers
         → Change-controlled
3
Verify and Report
Confirm deployment, track compliance
Compliance Check
WSUS/Intune/SCCM Report:
  Total endpoints: 5,000
  Patched:         4,850 (97%)
  Pending reboot:  100 (2%)
  Failed:          50 (1%)
  
Failed devices escalated to:
  → IT support ticket
  → 48-hour remediation SLA
  → Quarantine if not resolved

Patch Management Best Practices

Patch Management Implementation Guidelines

1. Know Your Assets: Can't patch what you don't know exists. Complete asset inventory is prerequisite.

2. Prioritize by Risk: Not all patches are equal. Focus on exploited, critical, internet-facing first.

3. Use Ring Deployment: Never push to all systems at once. Phased rollout catches issues early.

4. Automate Ruthlessly: Manual patching doesn't scale. Automate workstations; change-control servers.

5. Track SLA Compliance: Measure mean time to patch. Report to leadership. Tie to security KPIs.

6. Plan for Exceptions: Some systems can't be patched immediately. Compensating controls, documented risk acceptance.
