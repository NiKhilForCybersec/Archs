Security Architecture Principles

Core principles that guide the design and implementation of enterprise security architectures. These concepts form the foundation upon which all other security controls are built.

Defense in Depth

Defense in Depth is a security strategy that employs multiple layers of security controls throughout an IT system. If one layer fails, another layer is there to prevent or mitigate the attack. This approach acknowledges that no single security control is perfect.

Key Insight

Defense in Depth is not about adding redundant controls at each layer. Each layer should protect against different attack vectors or provide different types of protection. The goal is complementary coverage, not duplication.

Layer Responsibilities

Layer Primary Controls Protects Against
Perimeter NGFW, WAF, DDoS protection, Email security External attacks, volumetric attacks, known threats
Network Segmentation, IDS/IPS, NDR, DNS filtering Lateral movement, internal reconnaissance, C2
Endpoint EDR, AV, application control, host firewall Malware execution, exploitation, privilege escalation
Application Authentication, authorization, input validation Unauthorized access, injection attacks, logic flaws
Data Encryption, DLP, classification, access controls Data theft, unauthorized disclosure, tampering

Zero Trust Architecture

Zero Trust is a security model based on the principle of "never trust, always verify." Unlike traditional perimeter-based security that assumes everything inside the network is trusted, Zero Trust assumes breach and verifies every request as though it originates from an untrusted network.

Traditional Perimeter Model

Castle-and-Moat Approach

  • Trust based on network location
  • Inside network = trusted
  • Outside network = untrusted
  • VPN grants full network access
  • Flat internal network
  • Implicit trust after authentication
The Problem

Once an attacker breaches the perimeter (phishing, compromised VPN, insider threat), they have access to everything inside the network.

Zero Trust Model

Never Trust, Always Verify

  • No implicit trust based on location
  • Verify identity for every request
  • Verify device health/compliance
  • Least privilege access
  • Micro-segmentation
  • Continuous validation
The Solution

Even if an attacker compromises one user or system, they cannot move laterally. Every access request is individually verified.

Zero Trust Pillars

Identity

Strong authentication (MFA), risk-based access decisions, identity governance, and privileged access management.

Devices

Device compliance, health attestation, endpoint protection, mobile device management.

Network

Micro-segmentation, encrypted communications, network access control, software-defined perimeter.

Applications

Application-level access control, secure APIs, runtime protection, shadow IT discovery.

Data

Data classification, encryption, DLP, information rights management, access based on sensitivity.

Visibility & Analytics

Centralized logging, SIEM, UEBA, continuous monitoring, threat detection.

Principle of Least Privilege

The Principle of Least Privilege (PoLP) states that users, programs, and processes should only have the minimum permissions necessary to perform their intended function — nothing more. This limits the potential damage from accidents, errors, or attacks.

Excessive Privileges (The Problem)
Typical Bad Practices 
# User is domain admin "just in case"
net group "Domain Admins" jsmith /add

# Service account with full admin rights  
Grant-ADPermission -Full -Identity "svc_backup"

# Application uses sa account
connectionString="Server=sql;User=sa;Password=..."

# Everyone has read access to file shares
icacls "\\server\finance" /grant Everyone:R

Risk: Compromising any of these accounts grants attacker full access to critical systems.

Least Privilege (The Solution)
Best Practices 
# User has standard account, requests elevation
# via PAM for specific tasks with time limit

# Service account with minimum required permissions
New-ADServiceAccount -Name "svc_backup" 
Grant-Permission -Read -Path "\\backup\target"

# Application uses managed identity (no password)
connectionString="Server=sql;Authentication=ActiveDirectory"

# Role-based access to file shares
icacls "\\server\finance" /grant "Finance_Users":R

Result: Compromised account has limited blast radius. Attacker must escalate through multiple barriers.

Implementing Least Privilege

1
Inventory Access
Document all users, service accounts, and their current permissions. Identify who has access to what.
2
Define Roles
Create role definitions based on job functions. Map minimum required permissions to each role.
3
Remove Standing Privileges
Eliminate permanent admin access. Implement just-in-time (JIT) access via PAM solutions.
4
Regular Access Reviews
Conduct quarterly access certifications. Remove unused permissions automatically.
5
Monitor & Alert
Log all privilege usage. Alert on anomalous access patterns or privilege escalation attempts.

Separation of Duties

Separation of Duties (SoD) is a control that prevents any single individual from having the ability to complete a critical task alone. It requires collusion between multiple parties to commit fraud or cause significant harm.

Scenario Without SoD (Risk) With SoD (Control)
Financial Transactions Same person creates and approves payments One person creates, different person approves
User Provisioning Admin creates account and assigns all permissions HR requests, IT creates, manager approves access
Code Deployment Developer writes and deploys own code to production Dev writes, peer reviews, separate team deploys
Security Changes Single admin can disable security controls Changes require approval from security team + change board
Database Access DBA has full access to all data DBA manages schema, data access requires separate approval
Implementation Challenge

In smaller organizations, strict SoD may not be practical due to limited staff. In these cases, implement compensating controls like enhanced logging, regular audits, and management oversight of sensitive actions.

Assume Breach Mindset

The "assume breach" principle acknowledges that despite best efforts, determined attackers will eventually penetrate your defenses. Rather than focusing solely on prevention, organizations should invest equally in detection, response, and recovery capabilities.

Prevent

Block known threats and reduce attack surface. But accept that prevention will never be 100%.

Detect

Invest in visibility and monitoring. Assume attackers are already inside and hunt for them.

Respond

Have playbooks ready. Contain threats quickly to minimize damage. Practice incident response.

Recover

Plan for resilience. Maintain backups. Test disaster recovery. Return to operations quickly.

Practical Application

Ask yourself: "If an attacker got domain admin credentials right now, what would happen?" Then work backwards to add detection and containment controls at each step of that attack chain.

Security by Design

Security by Design means building security into systems from the beginning rather than adding it as an afterthought. It's significantly cheaper and more effective to address security during design than to retrofit it later.

Principle Description Example
Secure Defaults Systems should be secure out of the box Deny all network access by default; require explicit allow rules
Fail Secure When errors occur, fail to a secure state If authentication service is unavailable, deny access (don't bypass)
Complete Mediation Every access to every object must be checked Authorization checked on every API call, not just first request
Open Design Security shouldn't depend on secrecy of design Use proven encryption algorithms, not homegrown security
Economy of Mechanism Keep security mechanisms simple Simple code is easier to audit and has fewer bugs
Minimize Attack Surface Reduce exposed functionality and entry points Disable unused services, close unnecessary ports
