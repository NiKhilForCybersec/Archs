Multi-Factor Authentication (MFA)

MFA requires users to present two or more verification factors from different categories: something you know (password), something you have (phone/token), or something you are (biometric). MFA blocks 99.9% of account compromise attacks.

Authentication Factors

Something You Know

Passwords, PINs, security questions. Weakest factor — can be guessed, phished, or leaked in breaches.

Examples: Password, PIN, security question

Something You Have

Physical device possession. Stronger because attacker needs physical access to device.

Examples: Phone, hardware key, smart card

Something You Are

Biometric characteristics unique to the user. Hard to forge but raises privacy concerns.

Examples: Fingerprint, face, iris, voice

MFA Methods Comparison

Method Phishing Resistant User Experience Deployment Use Case
FIDO2/Passkeys ✓ Yes Excellent Moderate High-security, passwordless
Hardware Keys (YubiKey) ✓ Yes Good Complex (key mgmt) Privileged users, admins
Authenticator App (Push) Partial* Excellent Easy General workforce
Authenticator App (TOTP) ✗ No Good Easy Fallback method
SMS OTP ✗ No Good Very Easy Consumer, legacy
Phone Call ✗ No Fair Very Easy Accessibility fallback
*Push Notification Fatigue Attacks

Standard push notifications can be bypassed through "MFA fatigue" attacks where attackers spam push requests until user approves. Mitigations:

• Number Matching: User must enter a number shown on login screen (Microsoft Authenticator, Duo)

• Additional Context: Show location, app, device in push notification

• Rate Limiting: Block account after 3 denied push requests

Phishing-Resistant MFA

Phishable MFA (SMS, TOTP, Push)

User can be tricked into entering code on fake site:

1
Attacker sends phishing email
Link to fake login page (login.micros0ft.com)
2
User enters password on fake site
Attacker proxies to real site, triggers MFA
3
User enters OTP / approves push
Attacker captures and uses immediately
Phishing-Resistant (FIDO2/Passkeys)

Cryptographically bound to legitimate site origin:

1
Attacker sends phishing email
Link to fake login page (login.micros0ft.com)
2
FIDO2 key checks origin
Key bound to login.microsoft.com — won't sign for micros0ft.com
3
Attack fails
No credential provided — phishing blocked by design

MFA Implementation Best Practices

Success Factors

1. Require MFA for Everyone: No exceptions for executives or "trusted" users. Attackers specifically target high-value accounts.

2. Prioritize Phishing-Resistant Methods: Deploy FIDO2/Passkeys for privileged users first, then expand. Hardware keys for admins.

3. Enable Number Matching: If using push notifications, require number matching to prevent MFA fatigue attacks.

4. Block Legacy Authentication: Disable protocols that don't support MFA (IMAP, POP3, SMTP Auth, legacy Office clients).

5. Plan for Recovery: Establish secure MFA reset process. Require identity verification before resetting MFA.

6. Monitor MFA Events: Alert on MFA registration from new devices, multiple failed MFA attempts, and MFA bypass attempts.
