Conditional Access

Conditional Access is the Zero Trust control plane that makes access decisions based on identity, device, location, application, and risk signals. It's the "if-then" engine that determines whether to allow, block, or require additional verification for each access attempt.

The Access Decision Engine

Conditional Access evaluates multiple signals in real-time to make dynamic access decisions. Unlike traditional binary allow/deny, it can require step-up authentication, limit session capabilities, or enforce additional controls based on context.

Zero Trust in Action

Conditional Access is the practical implementation of Zero Trust's "never trust, always verify" principle. Every access request is evaluated against policy — whether the user is in the office, at home, or traveling abroad.

Traditional vs. Conditional Access

Traditional: Network-Based Access
  • On corporate network = trusted
  • VPN grants full access to everything
  • Same access from any device
  • Static allow/deny rules
  • MFA only for VPN connection
  • No risk-based adaptation

Baseline MFA All users, All apps Require MFA Universal second factor

Session Controls Deep Dive

Sign-in Frequency

How often users must re-authenticate. Default is 90 days for managed devices. Can be set as low as 1 hour for sensitive apps.

Use: High-security apps, kiosks

Persistent Browser

Whether "stay signed in" is allowed. Disable for shared devices or guest access.

Use: Shared workstations

App Enforced Restrictions

Passes session context to apps (SharePoint, Exchange) to enforce download blocks, print restrictions.

Use: Unmanaged device access

Defender for Cloud Apps

Routes session through CASB proxy for real-time monitoring, DLP, and block actions.

Use: Shadow IT control

Implementation Best Practices

Conditional Access Success Factors

1. Start with Report-Only: Deploy new policies in report-only mode first. Review sign-in logs to identify impact before enforcement.

2. Block Legacy Auth First: Legacy protocols (POP, IMAP, SMTP auth) bypass MFA. Block them before rolling out MFA policies.

3. Create Break-Glass Accounts: Exclude emergency access accounts from all policies. Test them monthly.

4. Use Named Locations: Define trusted IPs and countries. Reduces friction for known-good locations.

5. Layer Policies: Build from broad (all users, MFA) to specific (admins, phishing-resistant MFA, compliant device).

6. Combine with Identity Protection: Use risk-based policies to automatically respond to detected threats.

Common Mistakes

Locking yourself out: Always test policies with a pilot group. Have break-glass accounts excluded.

Forgetting service accounts: Service principals and app registrations may need exclusions or use workload identity.

Over-blocking: Start permissive, then tighten. It's easier to add restrictions than recover from outages.
