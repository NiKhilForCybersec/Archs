Serverless Security

Serverless computing (FaaS) shifts infrastructure responsibility to cloud providers, but application security remains your responsibility. Understanding the serverless threat model is essential for securing Lambda, Azure Functions, and Cloud Functions.

Shared Responsibility - Serverless

Serverless Threat Model

Injection Attacks

SQL injection, command injection, SSRF through function inputs. Validate and sanitize all inputs, especially from API Gateway, S3, SQS.

Over-Privileged Functions

Functions with excessive IAM permissions. If compromised, attacker has broad access. Principle of least privilege critical.

Vulnerable Dependencies

Third-party libraries with known CVEs. Attackers target npm, PyPI packages. Scan dependencies, keep updated.

Insecure Secrets

Hardcoded credentials, API keys in code or environment variables. Use Secrets Manager, rotate regularly.

Event Injection

Malicious data in event sources (S3, SNS, DynamoDB streams). Don't trust event data—validate everything.

Denial of Wallet

Attacker triggers excessive function invocations causing cost spike. Set concurrency limits, budget alerts.

Lambda IAM Best Practices

Least Privilege IAM Policy
# BAD: Overly permissive
{
  "Effect": "Allow",
  "Action": "s3:*",
  "Resource": "*"
}

# GOOD: Least privilege
{
  "Effect": "Allow",
  "Action": [
    "s3:GetObject",
    "s3:PutObject"
  ],
  "Resource": [
    "arn:aws:s3:::my-app-bucket/uploads/*"
  ],
  "Condition": {
    "StringEquals": {
      "s3:x-amz-server-side-encryption": "AES256"
    }
  }
}

# Best Practices:
# 1. One function = one role (don't share roles)
# 2. Specify exact resources (no wildcards)
# 3. Use conditions (VPC, encryption, source)
# 4. Use AWS IAM Access Analyzer to find unused permissions
# 5. Regular permission audits

Security Controls

Lambda Security Configuration
# Secure Lambda Configuration

resource "aws_lambda_function" "secure_function" {
  function_name = "secure-processor"
  runtime       = "python3.11"
  handler       = "main.handler"
  
  # VPC placement for network isolation
  vpc_config {
    subnet_ids         = [aws_subnet.private.id]
    security_group_ids = [aws_security_group.lambda.id]
  }
  
  # Environment variables from Secrets Manager
  environment {
    variables = {
      # Never hardcode secrets!
      DB_SECRET_ARN = aws_secretsmanager_secret.db.arn
    }
  }
  
  # Reserved concurrency to limit blast radius
  reserved_concurrent_executions = 100
  
  # Timeout to prevent runaway execution
  timeout = 30
  
  # Memory sizing (also affects CPU)
  memory_size = 256
  
  # Enable X-Ray tracing
  tracing_config {
    mode = "Active"
  }
  
  # Code signing for integrity
  code_signing_config_arn = aws_lambda_code_signing_config.this.arn
}

# Security group - restrict egress
resource "aws_security_group" "lambda" {
  egress {
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["10.0.0.0/8"]  # Only internal
  }
}

Serverless Security Best Practices

Serverless Security Guidelines

1. Minimal Permissions: Each function gets its own role with only required permissions. Audit regularly.

2. Validate All Input: Every event source (API Gateway, S3, SQS) is untrusted. Validate and sanitize.

3. Scan Dependencies: npm/pip packages have vulnerabilities. Scan in CI/CD, update regularly.

4. No Hardcoded Secrets: Use Secrets Manager or Parameter Store. Never in code or env vars.

5. VPC for Sensitive: Functions accessing databases should be in VPC with security groups.

6. Set Limits: Concurrency limits, timeouts, memory. Prevent denial of wallet attacks.
