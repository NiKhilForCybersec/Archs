Micro-Segmentation

Micro-segmentation creates granular security zones around individual workloads, applications, or even processes. Unlike traditional network segmentation (VLANs/firewalls), micro-segmentation is enforced at the host level, follows the workload, and enables zero trust within the data center.

Network Segmentation vs. Micro-Segmentation

Traditional Network Segmentation
  • Enforced at network layer (VLANs, firewalls)
  • Coarse-grained: entire subnets/zones
  • Static: tied to IP addresses
  • East-west traffic within zone is uncontrolled
  • Doesn't follow workloads (cloud migration breaks it)
  • Manual rule management at scale

Gap: Attacker compromises one server in app tier → can freely communicate with all other servers in same VLAN.

Micro-Segmentation
  • Enforced at host level (agent/hypervisor)
  • Fine-grained: per-workload, per-process
  • Dynamic: based on labels/tags, not IPs
  • Controls east-west within the same subnet
  • Follows workload to any environment
  • Policy automation with application context

Benefit: Attacker compromises one server → cannot reach any other server, even in same VLAN. Each workload is its own security zone.

Micro-Segmentation Architecture

Preventing Lateral Movement

Attack Scenario: Lateral Movement Blocked by Micro-Segmentation
1
Initial Compromise
Attacker exploits vulnerability in web server
Attack
Attacker exploits: CVE-2024-XXXX in Apache Struts
Target: WEB-SERVER-01 (10.100.1.10)
Result: Remote code execution achieved

Attacker now has shell access to web server
Next goal: Move laterally to database server
2
Reconnaissance Attempt
Attacker scans network from compromised host
Attacker Actions
# Attacker tries to scan the network
attacker@web-server:~$ nmap -sS 10.100.1.0/24

# Result with Micro-Segmentation:
Starting Nmap scan...
Nmap done: 256 IP addresses (0 hosts up)

# Why? Micro-seg agent blocks ALL outbound except:
#   - APP-SERVER-01:8080 (allowed by policy)
#   - Nothing else

# Attacker can't even see other hosts exist!
3
Direct Database Access Attempt
Attacker tries to connect directly to database
Blocked Attempt
# Attacker finds DB IP in config file
attacker@web-server:~$ cat /etc/app/db.conf
DB_HOST=10.100.1.30
DB_PORT=5432

# Tries direct connection
attacker@web-server:~$ psql -h 10.100.1.30 -U admin

# BLOCKED by micro-segmentation agent
Connection refused (filtered)

# Policy on WEB-SERVER-01:
#   ALLOW OUT: APP-SERVER-01:8080 ✓
#   ALLOW OUT: DB-SERVER-01:5432 ✗ NOT IN POLICY
#   DENY ALL OTHER
4
Lateral Movement to App Server
Attacker tries SSH, SMB, RDP to app server
All Protocols Blocked
# SSH attempt
attacker@web-server:~$ ssh 10.100.1.20
Connection refused

# SMB attempt  
attacker@web-server:~$ smbclient //10.100.1.20/share
Connection refused

# RDP attempt (if Windows)
Connection refused

# Only allowed connection: HTTP to port 8080
# But app server only accepts API calls, not shells

# Micro-seg policy is ALLOWLIST, not blocklist
# If it's not explicitly allowed, it's denied
5
Attack Contained
Attacker is trapped on single compromised host
Outcome
Attack Impact WITHOUT Micro-Segmentation:
  ✗ Web server compromised
  ✗ Lateral movement to app servers
  ✗ Credential harvesting
  ✗ Database access / data exfil
  ✗ Domain controller compromise
  Impact: CRITICAL - Full breach

Attack Impact WITH Micro-Segmentation:
  ✗ Web server compromised
  ✓ Lateral movement BLOCKED
  ✓ Database access BLOCKED
  ✓ Other servers protected
  Impact: LOW - Single host isolation

Time bought for defenders: Hours to days
Detection: Blocked connection attempts logged → SIEM alert

Implementation Approaches

Approach How It Works Pros Cons
Agent-Based Software agent on each host manages iptables/WFP Works anywhere (cloud, on-prem, containers) Agent deployment overhead
Hypervisor-Based Enforcement at vSwitch (VMware NSX) No agents needed for VMs VMware-only, doesn't cover physical
Cloud-Native AWS Security Groups, Azure NSGs Native integration, no extra cost Cloud-specific, limited visibility
Network-Based SDN fabric with micro-perimeters No host changes required Expensive, complex, vendor lock-in

Implementation Best Practices

Micro-Segmentation Success Factors

1. Start with Visibility: Deploy in monitor/visibility mode first. Understand traffic flows before enforcing policies.

2. Label Everything: Consistent labeling (app, env, tier, owner) enables dynamic policy. Tags > IP addresses.

3. Start with Ring-Fencing: Isolate critical assets first (databases, domain controllers). Don't try to segment everything at once.

4. Use Application Dependency Mapping: Let the platform discover communication patterns before writing rules.

5. Build Allowlists, Not Blocklists: Default deny, explicit allow. Never "block bad things" — only "allow known good."

6. Test in Simulation Mode: Most platforms let you test policies without enforcing. Validate before blocking traffic.
