Single Sign-On (SSO)

SSO allows users to authenticate once and access multiple applications without re-entering credentials. It improves user experience, reduces password fatigue, centralizes authentication policy, and enables consistent security controls like MFA across all applications.

Without SSO vs. With SSO

Without SSO (Siloed Auth)
  • Separate username/password per application
  • User manages 50+ passwords
  • Password reuse across apps (security risk)
  • Inconsistent MFA implementation
  • No central visibility of access
  • Offboarding requires disabling N accounts

Risk: User terminated → IT disables AD but forgets SaaS apps → ex-employee still has Salesforce access.

With SSO (Federated Identity)
  • One identity, one password, many apps
  • User authenticates once to IdP
  • Apps trust IdP assertion (no local password)
  • Consistent MFA at IdP level
  • Central audit trail of all access
  • Disable IdP account → all access revoked

Benefit: User terminated → disable Entra ID account → Salesforce, Slack, Zoom, GitHub all immediately inaccessible.

SSO Protocols

Protocol Full Name Use Case Token Format Transport
SAML 2.0 Security Assertion Markup Language Enterprise web apps, legacy XML assertion HTTP POST/Redirect
OIDC OpenID Connect (OAuth 2.0 + identity) Modern web/mobile apps, APIs JWT (id_token) HTTP + JSON
OAuth 2.0 Open Authorization API authorization (not auth) Access token HTTP + JSON
WS-Fed WS-Federation Microsoft legacy (ADFS) SAML token HTTP POST
SAML vs. OIDC: When to Use Which

Use SAML when: Integrating with enterprise SaaS (Salesforce, Workday, ServiceNow), legacy apps, or when the app only supports SAML.

Use OIDC when: Building modern apps, mobile apps, SPAs, or need to call APIs. OIDC is simpler, uses JSON, and is better for developers.

SAML 2.0 Authentication Flow

SP-Initiated SAML SSO (User Accesses Salesforce)
1
User Accesses Service Provider (Salesforce)
User navigates to contoso.my.salesforce.com
Initial Request
GET https://contoso.my.salesforce.com/
User: Not authenticated (no session)
Salesforce: "I don't know this user, redirect to IdP"
2
SP Redirects to Identity Provider
Salesforce generates SAML AuthnRequest and redirects user to Entra ID
SAML AuthnRequest
HTTP 302 Redirect to:
https://login.microsoftonline.com/{tenant}/saml2
  ?SAMLRequest=base64(deflate(AuthnRequest))
  &RelayState=https://contoso.my.salesforce.com/home

AuthnRequest (decoded):
<samlp:AuthnRequest
  ID="_abc123"
  Version="2.0"
  IssueInstant="2024-01-15T10:30:00Z"
  Destination="https://login.microsoftonline.com/..."
  AssertionConsumerServiceURL="https://contoso.my.salesforce.com/...">
  <saml:Issuer>https://contoso.my.salesforce.com</saml:Issuer>
</samlp:AuthnRequest>
3
User Authenticates at IdP
Entra ID prompts for credentials and MFA
Authentication
Entra ID Login Page:
  User enters: [email protected]
  Password: ********
  MFA: Authenticator push approved ✓

Entra ID validates:
  ✓ User exists in directory
  ✓ Password correct
  ✓ MFA satisfied
  ✓ Conditional Access: Allow (compliant device)
  ✓ User assigned to Salesforce Enterprise App
4
IdP Issues SAML Response
Entra ID creates signed SAML assertion and POSTs to Salesforce
SAML Response
HTTP POST to: https://contoso.my.salesforce.com/saml/acs

SAMLResponse (simplified):
<samlp:Response>
  <saml:Assertion>
    <saml:Issuer>https://sts.windows.net/{tenant}/</saml:Issuer>
    
    <saml:Subject>
      <saml:NameID>[email protected]</saml:NameID>
    </saml:Subject>
    
    <saml:Conditions NotBefore="..." NotOnOrAfter="...">
      <saml:AudienceRestriction>
        <saml:Audience>https://contoso.my.salesforce.com</saml:Audience>
      </saml:AudienceRestriction>
    </saml:Conditions>
    
    <saml:AttributeStatement>
      <saml:Attribute Name="email">[email protected]</saml:Attribute>
      <saml:Attribute Name="firstName">John</saml:Attribute>
      <saml:Attribute Name="lastName">Smith</saml:Attribute>
      <saml:Attribute Name="groups">Sales-Team</saml:Attribute>
    </saml:AttributeStatement>
    
    <ds:Signature>...RSA-SHA256 signature...</ds:Signature>
  </saml:Assertion>
</samlp:Response>
5
SP Validates Assertion & Creates Session
Salesforce validates signature, creates local session
Validation
Salesforce Validation:
  ✓ Signature valid (using IdP public certificate)
  ✓ Assertion not expired (NotOnOrAfter check)
  ✓ Audience matches (https://contoso.my.salesforce.com)
  ✓ User [email protected] exists in Salesforce
  
Session Created:
  User: John Smith ([email protected])
  Profile: Sales User
  Permissions: Based on Salesforce profile + groups attribute
  
Redirect to: https://contoso.my.salesforce.com/home
Result: User is logged in to Salesforce ✓

OIDC Authentication Flow

Authorization Code Flow (Web Application)
1
Application Redirects to IdP
App redirects user to Entra ID authorization endpoint
Authorization Request
GET https://login.microsoftonline.com/{tenant}/oauth2/v2.0/authorize
  ?client_id=app-client-id-guid
  &response_type=code
  &redirect_uri=https://app.contoso.com/callback
  &scope=openid profile email
  &state=random-csrf-token
  &nonce=random-replay-protection
2
User Authenticates
User logs in at IdP (same as SAML)
3
IdP Returns Authorization Code
Entra ID redirects back with short-lived code
Callback
GET https://app.contoso.com/callback
  ?code=OAQABAAIAAAAm-06blBE...
  &state=random-csrf-token

App validates: state matches (CSRF protection)
4
App Exchanges Code for Tokens
Backend calls token endpoint with code + client secret
Token Exchange
POST https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=OAQABAAIAAAAm-06blBE...
&redirect_uri=https://app.contoso.com/callback
&client_id=app-client-id
&client_secret=app-secret

Response:
{
  "access_token": "eyJ0eXAiOiJKV1QiLCJhbGciOi...",
  "id_token": "eyJ0eXAiOiJKV1QiLCJhbGciOi...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "OAQABAAAAAAm-06blBE..."
}
5
App Validates ID Token
Decode JWT, verify signature, extract user info
ID Token (Decoded)
{
  "iss": "https://login.microsoftonline.com/{tenant}/v2.0",
  "sub": "user-object-id",
  "aud": "app-client-id",
  "exp": 1705320000,
  "iat": 1705316400,
  "nonce": "random-replay-protection",
  "name": "John Smith",
  "preferred_username": "[email protected]",
  "email": "[email protected]",
  "groups": ["Sales-Team", "All-Employees"]
}

Validation:
  ✓ Signature valid (RS256, IdP public key)
  ✓ iss matches expected issuer
  ✓ aud matches our client_id
  ✓ exp > current time (not expired)
  ✓ nonce matches (replay protection)

SSO Best Practices

SSO Implementation Success Factors

1. SSO Everything: Every SaaS app should use SSO. Local accounts are security debt. No exceptions for "small" apps.

2. Enforce MFA at IdP: If MFA is required at the IdP, all SSO apps inherit that protection automatically.

3. Use Conditional Access: Block access from unmanaged devices, high-risk locations, or compromised accounts — applies to all apps.

4. Disable Local Auth: After enabling SSO, disable local username/password authentication in the app if possible.
