API Security

APIs are the backbone of modern applications—and a prime target for attackers. API security requires proper authentication, authorization, input validation, rate limiting, and continuous monitoring. The OWASP API Security Top 10 outlines the most critical API vulnerabilities.

OWASP API Security Top 10 (2023)

Risk Description Mitigation
API1: Broken Object Level Authorization Access other users' data by changing IDs Verify user owns requested resource
API2: Broken Authentication Weak auth, token issues, credential stuffing Strong auth, MFA, token best practices
API3: Broken Object Property Level Auth Mass assignment, excessive data exposure Whitelist allowed properties
API4: Unrestricted Resource Consumption No rate limits, DoS via expensive operations Rate limiting, pagination, quotas
API5: Broken Function Level Auth Access admin functions as regular user Enforce role-based access on all endpoints
API6: Unrestricted Access to Sensitive Business Flows Abuse business logic (ticket scalping, etc.) Detect automated abuse, CAPTCHA
API7: Server-Side Request Forgery Fetch URLs, access internal systems Validate/sanitize URLs, blocklist internal
API8: Security Misconfiguration Debug enabled, verbose errors, CORS Hardening, security headers, review configs
API9: Improper Inventory Management Shadow APIs, deprecated endpoints still live API discovery, documentation, versioning
API10: Unsafe Consumption of APIs Trusting third-party API responses blindly Validate all external data, timeouts

API1: Broken Object Level Authorization (BOLA)

BOLA Attack and Prevention
1
Attacker Discovers Pattern
User IDs are sequential integers
Normal Request
GET /api/v1/users/12345/profile
Authorization: Bearer eyJhbGc...

Response 200:
{
  "id": 12345,
  "name": "John Smith",
  "email": "[email protected]",
  "ssn": "123-45-6789",      ← PII
  "salary": 85000            ← Sensitive
}
2
BOLA Attack
Change ID to access other users' data
Malicious Request
# Attacker changes 12345 → 12346
GET /api/v1/users/12346/profile
Authorization: Bearer eyJhbGc...   ← Same token (user 12345)

# VULNERABLE API RETURNS:
Response 200:
{
  "id": 12346,
  "name": "Jane Doe",           ← Different user's data!
  "email": "[email protected]",
  "ssn": "987-65-4321",
  "salary": 120000
}

# Attacker iterates: 12347, 12348, 12349...
# Mass data exfiltration
3
Secure Implementation
Verify ownership before returning data
Secure API Code
@app.route('/api/v1/users//profile')
@require_auth
def get_profile(user_id):
    # Extract user from token
    requesting_user = get_user_from_token(request.headers['Authorization'])
    
    # CRITICAL: Verify ownership
    if str(requesting_user.id) != user_id:
        # Check if admin (role-based exception)
        if not requesting_user.has_role('admin'):
            return {"error": "Forbidden"}, 403
    
    # Safe to return data
    user = User.query.get(user_id)
    return user.to_dict()

# Additional protections:
# - Use UUIDs instead of sequential IDs
# - Log all access for audit trail
# - Rate limit to prevent enumeration

JWT Validation Best Practices
import jwt
from jwt.exceptions import InvalidTokenError

def validate_jwt(token: str) -> dict:
    try:
        # CRITICAL: Always specify algorithm (prevent "none" attack)
        payload = jwt.decode(
            token,
            key=PUBLIC_KEY,
            algorithms=["RS256"],  # Whitelist algorithms
            audience="api.company.com",  # Validate audience
            issuer="https://auth.company.com",  # Validate issuer
        )
        
        # Additional validations
        if payload['exp'] < time.time():
            raise InvalidTokenError("Token expired")
            
        if payload['iat'] > time.time():
            raise InvalidTokenError("Token issued in future")
            
        return payload
        
    except InvalidTokenError as e:
        logger.warning(f"Invalid JWT: {e}")
        raise AuthenticationError("Invalid token")

# Common JWT Vulnerabilities to Prevent:
# - Algorithm confusion (HS256 vs RS256)
# - Missing signature validation
# - Not checking expiration
# - Accepting "none" algorithm

Rate Limiting

API Gateway Rate Limit Configuration
# Kong API Gateway rate limiting
plugins:
  - name: rate-limiting
    config:
      minute: 100          # 100 requests per minute
      hour: 1000           # 1000 requests per hour
      policy: redis        # Distributed rate limiting
      fault_tolerant: true
      hide_client_headers: false
      
  # Per-endpoint limits for sensitive operations
  - name: rate-limiting
    route: login-route
    config:
      minute: 10           # Only 10 login attempts per minute
      hour: 50             # Prevent credential stuffing
      
  - name: rate-limiting
    route: password-reset
    config:
      minute: 3            # Very strict for password reset
      hour: 10

# Response Headers:
# X-RateLimit-Limit: 100
# X-RateLimit-Remaining: 47
# X-RateLimit-Reset: 1705320000

# When exceeded:
# HTTP 429 Too Many Requests
# Retry-After: 60

API Security Best Practices

API Security Implementation Guidelines

1. Authentication on Every Endpoint: No endpoint should be accessible without authentication (except truly public data).

2. Authorization at Object Level: Always verify the user has permission to access the specific resource they're requesting.

3. Input Validation: Validate all inputs against a schema. Reject unexpected fields, types, and values.

4. Rate Limit Everything: Protect against DoS and enumeration. Stricter limits on sensitive endpoints (login, password reset).

5. Inventory Your APIs: Know every API endpoint. Shadow APIs are a major risk. Use API discovery tools.

6. Log and Monitor: Log all API calls with context. Alert on anomalies (unusual patterns, error spikes, BOLA attempts).
