Service Accounts & Workload Identity

Service accounts are non-human identities used by applications, services, and automated processes. They represent one of the largest and most overlooked attack surfaces in enterprise environments. Modern workload identity approaches eliminate static credentials entirely.

The Service Account Problem

Traditional Service Accounts
  • Static passwords that never expire
  • Passwords stored in config files, scripts, code
  • Over-privileged (often Domain Admin "just in case")
  • No owner, no lifecycle management
  • Shared across multiple applications
  • Never audited, never rotated

Risk: Attacker finds svc_backup password in script → account has Domain Admin → complete compromise in minutes.

Modern Workload Identity
  • No static passwords (managed identities)
  • Short-lived, auto-rotating credentials
  • Least privilege, scoped permissions
  • Clear ownership and lifecycle
  • One identity per workload
  • Continuous monitoring and attestation

Benefit: App uses managed identity → no password to steal → access only to specific resources → automatic credential rotation.

Types of Non-Human Identities

Type Platform Credential Best Practice
AD Service Account Active Directory Password Use gMSA (Group Managed Service Account)
gMSA Active Directory Auto-rotated by AD Preferred for Windows services
Service Principal Entra ID / Azure Client Secret or Certificate Use certificates, enable rotation
Managed Identity Azure None (automatic) Always prefer over service principals
IAM Role AWS Temporary STS credentials Use roles, not IAM users with keys
Service Account GCP JSON key or Workload Identity Use Workload Identity Federation
API Keys Various SaaS Static token Store in vault, rotate regularly

Managed Identity Deep Dive (Azure)

System-Assigned Managed Identity: Zero Credentials
1
Enable Managed Identity on Resource
Azure automatically creates identity tied to resource lifecycle
Azure CLI
# Enable system-assigned managed identity on App Service
az webapp identity assign --name my-webapp --resource-group my-rg

# Result:
{
  "principalId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "tenantId": "contoso.onmicrosoft.com",
  "type": "SystemAssigned"
}

# Identity created in Entra ID automatically
# No password, no certificate, no secrets to manage!
2
Grant Permissions (RBAC)
Assign least-privilege access to target resources
Role Assignment
# Grant access to specific Storage Account
az role assignment create \
  --assignee a1b2c3d4-e5f6-7890-abcd-ef1234567890 \
  --role "Storage Blob Data Reader" \
  --scope "/subscriptions/.../storageAccounts/mystorage"

# Grant access to Key Vault secrets
az role assignment create \
  --assignee a1b2c3d4-e5f6-7890-abcd-ef1234567890 \
  --role "Key Vault Secrets User" \
  --scope "/subscriptions/.../vaults/my-keyvault"

# Permissions are scoped to SPECIFIC resources
# NOT blanket access to entire subscription
3
Application Uses Identity (No Credentials!)
App authenticates automatically via Azure IMDS
Application Code
// C# - Using DefaultAzureCredential (recommended)
var blobClient = new BlobServiceClient(
    new Uri("https://mystorage.blob.core.windows.net"),
    new DefaultAzureCredential()  // Automatically uses managed identity
);

// Python
from azure.identity import DefaultAzureCredential
from azure.storage.blob import BlobServiceClient

credential = DefaultAzureCredential()
blob_service = BlobServiceClient(
    "https://mystorage.blob.core.windows.net",
    credential=credential
)

// How it works:
// 1. App calls Azure Instance Metadata Service (IMDS)
// 2. IMDS returns short-lived access token
// 3. Token used to authenticate to Azure services
// 4. Token auto-refreshes before expiry
// 
// NO credentials in code, config, or environment variables!

Group Managed Service Accounts (gMSA)

gMSA: Auto-Rotating AD Service Accounts
1
Traditional Service Account Problems
Why gMSA exists
The Problem
Traditional AD Service Account:
  Account: svc_sqlbackup
  Password: Summer2019!  (set 5 years ago)
  Password Expiry: Never
  Used by: 47 different servers
  Stored in: Plain text config files, scripts, scheduled tasks
  
Issues:
  ✗ Password never rotates
  ✗ If password changes, 47 services break
  ✗ Password known by multiple admins
  ✗ Password in version control (git history)
  ✗ Kerberoastable (SPN → offline cracking)
2
gMSA Solution
Active Directory manages the password automatically
gMSA Setup
# Create gMSA in Active Directory
New-ADServiceAccount -Name "gMSA_SQLBackup" `
  -DNSHostName "gMSA_SQLBackup.contoso.com" `
  -PrincipalsAllowedToRetrieveManagedPassword "SQL-Servers-Group"

# Install on target server
Install-ADServiceAccount -Identity "gMSA_SQLBackup"

# Configure service to use gMSA
# Account: CONTOSO\gMSA_SQLBackup$
# Password: (leave blank - AD manages it)

Benefits:
  ✓ 240-character random password
  ✓ Auto-rotates every 30 days
  ✓ Only authorized computers can retrieve password
  ✓ No human ever knows the password
  ✓ Service automatically gets new password
  ✓ Works with SQL Server, IIS, scheduled tasks

Service Account Attack Vectors

Kerberoasting

Request service ticket for any SPN, crack password offline. Especially dangerous for accounts with weak passwords.

Mitigation: gMSA, 25+ char passwords, monitor ticket requests

Credential Exposure

Passwords in scripts, config files, environment variables, git repos, documentation, ServiceNow tickets.

Mitigation: Vault storage, managed identities, secret scanning

Over-Privileged Accounts

"It needs Domain Admin to work" - actually needs read access to one share. Now attacker has DA.

Mitigation: Least privilege reviews, PAM for privileged service accounts

No Lifecycle Management

Service decommissioned but account remains. Now orphaned with privileges nobody monitors.

Mitigation: Ownership tracking, regular attestation, auto-disable

Service Account Best Practices

Service Account Security Guidelines

1. Eliminate Static Credentials: Use managed identities (Azure), IAM roles (AWS), Workload Identity (GCP), or gMSA (AD) whenever possible.

2. Vault Everything Else: If you must have credentials, store in HashiCorp Vault, Azure Key Vault, AWS Secrets Manager. Never in code or config.

3. One Identity Per Workload: Don't share service accounts across applications. Compromise of one shouldn't affect others.

4. Least Privilege Always: Service accounts should have minimum permissions needed. Review regularly. If it doesn't need DA, it shouldn't have DA.

5. Enforce Ownership: Every service account must have an owner. Orphaned accounts get disabled automatically.

6. Monitor and Alert: Service accounts should have predictable behavior. Alert on anomalies: unusual hours, unusual targets, unusual volumes.
