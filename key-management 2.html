Key Management

Encryption is only as strong as your key management. Keys must be generated securely, stored safely, rotated regularly, and destroyed properly. Hardware Security Modules (HSMs) and Key Management Services (KMS) provide the foundation for enterprise key management.

Key Hierarchy

Envelope Encryption

Data is encrypted with a Data Encryption Key (DEK). The DEK is encrypted with a Key Encryption Key (KEK). The KEK is protected by a Master Key in the HSM. This hierarchy means rotating the master key only requires re-encrypting the KEKs, not all data.

HSM vs Software KMS

Hardware Security Module (HSM)
  • Tamper-resistant hardware device
  • Keys never leave the HSM
  • FIPS 140-2 Level 3 certified
  • Cryptographic operations in hardware
  • Physical security controls
  • Higher cost, complex setup

Use for: Root CA keys, master encryption keys, payment processing, regulatory requirements (PCI-DSS, HIPAA)

Cloud KMS (Software)
  • Managed service, API-driven
  • Backed by HSM (provider-managed)
  • Easy integration with cloud services
  • Automatic key rotation
  • Pay-per-use pricing
  • Lower cost, quick setup

Use for: Application encryption keys, database TDE, S3/blob encryption, general workloads

Key Rotation

AWS KMS Automatic Key Rotation
1
Enable Auto-Rotation
Configure key for annual rotation
AWS CLI
# Enable automatic rotation (yearly)
aws kms enable-key-rotation --key-id alias/my-key

# Check rotation status
aws kms get-key-rotation-status --key-id alias/my-key
{
  "KeyRotationEnabled": true
}
2
KMS Creates New Key Material
Old key material retained for decryption
What Happens
Year 1: Key material v1 created
  - All encryptions use v1
  - All decryptions use v1

Year 2: Key material v2 created (rotation)
  - NEW encryptions use v2
  - Decryptions: KMS automatically selects v1 or v2
    based on ciphertext metadata

Year 3: Key material v3 created (rotation)
  - NEW encryptions use v3
  - Decryptions: v1, v2, or v3 as needed

Key ID remains the same! No application changes needed.
3
Transparent to Applications
Same key alias works with all versions
Application Code (Unchanged)
# Encrypt (always uses latest key material)
aws kms encrypt \
  --key-id alias/my-key \
  --plaintext "sensitive data"

# Decrypt (KMS selects correct key version automatically)
aws kms decrypt \
  --ciphertext-blob fileb://encrypted.bin

# No code changes needed when key rotates!
# KMS handles version selection transparently

Bring Your Own Key (BYOK)

Import Your Own Key to AWS KMS
# 1. Create KMS key with external origin
aws kms create-key \
  --origin EXTERNAL \
  --description "Customer-managed imported key"

# 2. Get import parameters (wrapping key)
aws kms get-parameters-for-import \
  --key-id 1234abcd-... \
  --wrapping-algorithm RSAES_OAEP_SHA_256 \
  --wrapping-key-spec RSA_2048

# 3. Generate your key material (on your HSM)
openssl rand 32 > key-material.bin

# 4. Wrap key material with KMS wrapping key
openssl pkeyutl -encrypt \
  -in key-material.bin \
  -out wrapped-key.bin \
  -pubin -inkey wrapping-key.pem \
  -pkeyopt rsa_padding_mode:oaep \
  -pkeyopt rsa_oaep_md:sha256

# 5. Import to KMS
aws kms import-key-material \
  --key-id 1234abcd-... \
  --encrypted-key-material fileb://wrapped-key.bin \
  --import-token fileb://import-token.bin \
  --expiration-model KEY_MATERIAL_DOES_NOT_EXPIRE

# BYOK Benefits:
# - You control key generation
# - Meet regulatory requirements
# - Enable cloud exit strategy (you have copy of key)
# 
# BYOK Limitations:
# - No automatic rotation (must re-import)
# - You're responsible for key backup
# - More operational complexity

Key Management Best Practices

Key Management Implementation Guidelines

1. Use Key Hierarchy: Master → KEK → DEK structure. Limits blast radius of key compromise.

2. HSM for Root Keys: Master keys and CA private keys in HSM. Never exportable, never in software.

3. Enable Automatic Rotation: Annual minimum for cloud KMS. Quarterly for high-sensitivity applications.

4. Separate Keys by Purpose: Different keys for different data classifications. Don't reuse encryption keys for signing.

5. Audit Key Usage: Log every key operation. Alert on unusual access patterns or denied requests.

6. Plan for Key Recovery: Documented procedures for key recovery. Test recovery process annually.
