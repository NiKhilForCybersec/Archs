Data Loss Prevention (DLP)

DLP solutions detect and prevent unauthorized transmission of sensitive data across endpoint, network, and cloud channels. This guide covers architecture patterns, policy enforcement flows, and migration strategies.

What is DLP?

Data Loss Prevention (DLP) is a set of tools and processes that ensure sensitive data is not lost, misused, or accessed by unauthorized users. DLP solutions inspect content in motion (network), at rest (storage), and in use (endpoints) to enforce data handling policies.

Key Concept

DLP is not just about blocking data exfiltration. Modern DLP focuses on visibility first — understanding where sensitive data exists and how it flows — before implementing enforcement controls.

DLP Deployment Models

Endpoint DLP

Agent on device monitors clipboard, USB, print, screen capture, and application data transfers.

Data in Use

Network DLP

Inline or out-of-band inspection of network traffic including email, web, and file transfers.

Data in Motion

Cloud DLP

API-based and inline inspection for SaaS apps, cloud storage, and cloud email.

Cloud Data

Storage DLP

Discovery and classification of sensitive data at rest in file shares, databases, and repositories.

Data at Rest

Traditional vs. Modern DLP Architecture

Traditional On-Premises DLP

Symantec DLP / Digital Guardian / Forcepoint

  • On-premises management server
  • Separate endpoint, network, and storage components
  • Heavy endpoint agent (performance impact)
  • Network appliances for traffic inspection
  • Manual policy tuning required
  • Limited cloud visibility
  • Complex deployment and maintenance

DLP Migration Strategy: Legacy to Purview

Migration Principle

DLP migrations should follow a phased approach: first achieve parity in audit mode, then gradually enable enforcement. Never migrate directly to blocking without extensive testing.

1
Phase 1: Discovery & Assessment (4-6 weeks)
Export existing policies from legacy DLP. Map sensitive information types to Purview equivalents. Identify gaps requiring custom SITs.
Policy Mapping Example 
Legacy Symantec Policy          → Purview Equivalent
─────────────────────────────────────────────────────
Credit Card Detection           → Credit Card Number (built-in)
Custom SSN Pattern              → U.S. SSN (built-in)
Project Codenames (regex)       → Custom SIT (create new)
Source Code Detection           → Source Code (built-in)
Customer PII Combo              → Custom SIT + Trainable Classifier
2
Phase 2: Parallel Deployment — Audit Mode (6-8 weeks)
Deploy Purview policies in audit-only mode alongside legacy DLP. Compare detection rates and tune false positives.
Comparison Metrics 
Weekly Comparison Report:
─────────────────────────────────────────
Metric                 Legacy    Purview
─────────────────────────────────────────
Total Incidents        1,247     1,189
True Positives           892       934  ← Purview better
False Positives          355       255  ← Purview better  
Unique Files Detected  2,341     2,456
Avg Detection Latency    45s       12s  ← Purview faster
─────────────────────────────────────────
Status: Ready for Phase 3 when within 5%
3
Phase 3: Gradual Enforcement (4-6 weeks)
Enable enforcement on Purview policies starting with least-risk channels. Progress from Warn → Block with Override → Block.
Enforcement Rollout 
Week 1-2: Enable "Warn" on Exchange Online
Week 3-4: Enable "Warn" on SharePoint/OneDrive  
Week 5-6: Enable "Block with Override" on Email
Week 7-8: Enable "Block with Override" on Endpoints
Week 9+:  Enable "Block" on critical policies

Rollback Plan: Disable Purview policy, legacy still active
4
Phase 4: Decommission Legacy (2-4 weeks)
Once Purview is fully enforcing, disable legacy DLP policies. Maintain legacy in monitor-only as safety net, then fully remove.

DLP Implementation Best Practices

Key Recommendations

1. Start with Audit Mode: Always deploy new policies in audit mode first. Analyze for 2-4 weeks before enabling enforcement.

2. Focus on Crown Jewels: Don't try to protect everything. Identify your most sensitive data types and start there.

3. Use Sensitivity Labels: Labels provide persistent protection that follows the document. DLP + Labels is more powerful than DLP alone.

4. Tune False Positives Aggressively: High false positive rates lead to user fatigue and policy bypass attempts.

5. Communicate with Users: Provide clear policy tips explaining WHY actions are blocked and how to proceed legitimately.

6. Monitor Override Abuse: If users constantly override policies, either the policy is too strict or training is needed.

7. Integrate with Incident Response: High-severity DLP incidents should trigger SOC workflows, not just compliance reports.
