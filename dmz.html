DMZ Architecture

A DMZ (Demilitarized Zone) is a network segment that sits between the untrusted internet and the trusted internal network. It hosts public-facing services while providing an additional layer of security to protect internal resources from direct internet exposure.

Why Use a DMZ?

No DMZ (Direct Exposure)
  • Web server on internal network
  • Firewall allows internet → internal
  • Compromise = direct internal access
  • Web server can reach everything
  • Single firewall, single failure point

Risk: Web app exploit → attacker on internal network → lateral movement to DC, databases, file shares.

With DMZ (Layered Defense)
  • Web server in isolated DMZ
  • Two firewalls (front + back)
  • Compromise contained in DMZ
  • Backend access via restricted ports only
  • Defense in depth architecture

Benefit: Web app exploit → attacker in DMZ → can only reach backend API on port 443 → internal network protected.

  ✓ XSS: Not detected
  ✓ Rate limit: 45/100 requests/min (OK)

  Backend pool: 10.200.1.0/24 (Internal app servers)
  Health check: 10.200.1.11 (healthy)
  Forward to: 10.200.1.11:8443
4
Internal Firewall Processing
Traffic crosses from DMZ to internal network
Internal Firewall
Internal Firewall Evaluation:
  Source: 10.100.1.10 (DMZ Web Server)
  Destination: 10.200.1.11:8443 (App Server)
  
  Rule: "Allow-DMZ-to-AppServers"
  Source Zone: DMZ
  Destination Zone: App-Tier
  Source: DMZ-WebServers (group)
  Destination: App-Servers (group)
  Service: tcp/8443 ONLY
  Action: ALLOW

    - Database tier (tcp/1433) - DENIED
    - Domain controllers - DENIED
    - Workstations - DENIED
    - Other DMZ servers - DENIED

Response Flow:
  App Server (10.200.1.11)

Total Inspection Points: 4

  2. WAF (application layer)
  3. Internal FW (DMZ→Internal)
  4. Internal FW (return traffic - stateful)

DMZ Design Patterns

Pattern Description Use Case Complexity
Single Firewall (3-leg) One firewall with 3 interfaces: internet, DMZ, internal Small environments, cost-sensitive Low
Dual Firewall Separate edge and internal firewalls Enterprise standard, defense in depth Medium
Multi-Tier DMZ Web tier, app tier, data tier — each isolated High-security apps, PCI environments High
Cloud DMZ Virtual DMZ in cloud (Azure/AWS subnet isolation) Cloud-native applications Medium

What Belongs in a DMZ

✓ DMZ-Appropriate

  • Web servers (static content)
  • Reverse proxies / load balancers
  • Web Application Firewalls
  • Email gateways (MTA)
  • VPN concentrators
  • DNS servers (external)
  • FTP/SFTP servers
  • API gateways

✗ Never in DMZ

  • Domain Controllers
  • Databases with sensitive data
  • File servers
  • Internal DNS/DHCP
  • Backup systems
  • Management consoles
  • User workstations
  • Certificate authorities

DMZ Best Practices

DMZ Implementation Guidelines

1. Use Different Firewall Vendors: If external is Palo Alto, make internal Cisco. A 0-day in one doesn't compromise both.

2. No Direct Internet to Internal: All traffic must traverse DMZ. No firewall rules allowing internet directly to internal network.

3. Restrict DMZ to DMZ Traffic: DMZ servers shouldn't communicate with each other unless required. Prevents lateral movement within DMZ.

4. Minimal Services: DMZ servers run only what's needed. No unnecessary services, no development tools, no SSH from internet.

5. Harden Aggressively: DMZ hosts are most exposed. Patch immediately, minimal software, host-based firewalls, EDR required.

6. Monitor Everything: Full packet capture, all logs to SIEM, behavioral analysis. DMZ is where attacks start.
