Authentication Protocols

Authentication protocols define how users and systems prove their identity. Understanding Kerberos, SAML, OAuth, and OIDC is essential for implementing secure authentication across on-premises and cloud environments.

Protocol Comparison

Protocol Purpose Use Case Token Type
Kerberos Authentication On-premises AD, Windows domain Tickets (TGT, Service)
SAML 2.0 Authentication + Authorization Enterprise SSO, federation XML Assertions
OAuth 2.0 Authorization only API access, delegated permissions Access Token
OIDC Authentication + Authorization Modern SSO, mobile, SPA ID Token + Access Token

Kerberos Authentication

Kerberos Authentication Flow
Kerberos Step-by-Step
# Kerberos Authentication (Active Directory)

1. AS-REQ: User → KDC (Domain Controller)
   ┌─────────────────────────────────────────┐
   │ "I am jsmith, here's proof (encrypted   │
   │  timestamp with my password hash)"       │
   └─────────────────────────────────────────┘

2. AS-REP: KDC → User
   ┌─────────────────────────────────────────┐
   │ TGT (Ticket Granting Ticket)            │
   │ - Encrypted with KRBTGT hash            │
   │ - Contains user identity, groups        │
   │ - Valid for 10 hours (default)          │
   └─────────────────────────────────────────┘

3. TGS-REQ: User → KDC
   ┌─────────────────────────────────────────┐
   │ "I have TGT, give me ticket for        │
   │  HTTP/webapp.company.com"               │
   └─────────────────────────────────────────┘

4. TGS-REP: KDC → User
   ┌─────────────────────────────────────────┐
   │ Service Ticket                          │
   │ - Encrypted with service's password     │
   │ - Contains user identity for service    │
   └─────────────────────────────────────────┘

5. AP-REQ: User → Service
   ┌─────────────────────────────────────────┐
   │ "Here's my service ticket"              │
   │ Service decrypts, validates, grants     │
   │ access based on user's group membership │
   └─────────────────────────────────────────┘

Key Security Points:
  • Password never sent over network
  • Tickets are time-limited
  • Mutual authentication possible
  • Vulnerable to: Kerberoasting, Golden Ticket, Pass-the-Ticket

# OIDC (Modern)
┌────────────────────────────────────────────────┐
│ Format: JSON                                    │
│ Token: JWT (ID Token + Access Token)           │
│ Signing: JWS (JSON Web Signature)              │
│ Best for: Mobile, SPA, APIs, modern apps       │
│ Built on: OAuth 2.0                            │
└────────────────────────────────────────────────┘

ID Token (JWT payload):
{
  "iss": "https://login.microsoftonline.com/...",
  "sub": "abc123",
  "aud": "app-client-id",
  "exp": 1699999999,
  "iat": 1699996399,
  "name": "John Smith",
  "email": "[email protected]",
  "groups": ["Admins", "Developers"]
}

When to use which:
  SAML: Legacy enterprise apps, established SSO
  OIDC: New development, mobile, APIs, SPA

Protocol Security Best Practices

Authentication Protocol Guidelines

1. Prefer OIDC for New Apps: Modern, JSON-based, mobile-friendly. SAML for legacy only.

2. Validate Tokens Properly: Check signature, issuer, audience, expiration. Don't trust without verification.

3. Use Authorization Code + PKCE: For public clients (mobile, SPA). Never use implicit flow.

4. Short Token Lifetimes: Access tokens 1 hour or less. Use refresh tokens for longer sessions.

5. Secure Kerberos: Disable RC4, use AES. Protect KRBTGT. Monitor for Kerberoasting.

6. Centralize Identity: One IdP, federate to applications. Avoid password sprawl.
