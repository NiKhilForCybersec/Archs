Threat Modeling

Threat modeling is a structured approach to identifying security threats, vulnerabilities, and countermeasures early in design. It answers: What are we building? What can go wrong? What are we doing about it?

Threat Modeling Process

Four Question Framework
# Threat Modeling Four Questions (Adam Shostack)

1. WHAT ARE WE WORKING ON?
   ┌────────────────────────────────────────────────────┐
   │ • System architecture diagram                      │
   │ • Data flow diagram (DFD)                         │
   │ • Trust boundaries                                 │
   │ • Assets and entry points                          │
   └────────────────────────────────────────────────────┘
                            │
2. WHAT CAN GO WRONG?
   ┌────────────────────────────────────────────────────┐
   │ • Apply STRIDE to each component                  │
   │ • Identify threats at trust boundaries            │
   │ • Consider attacker motivations                    │
   │ • Review historical vulnerabilities                │
   └────────────────────────────────────────────────────┘
                            │
3. WHAT ARE WE GOING TO DO ABOUT IT?
   ┌────────────────────────────────────────────────────┐
   │ • Mitigate: Implement controls                    │
   │ • Transfer: Insurance, SLA with vendor            │
   │ • Accept: Document risk acceptance                │
   │ • Avoid: Remove feature/component                 │
   └────────────────────────────────────────────────────┘
                            │
4. DID WE DO A GOOD JOB?
   ┌────────────────────────────────────────────────────┐
   │ • Review completeness                              │
   │ • Validate with security team                     │
   │ • Test mitigations                                 │
   │ • Update when architecture changes                │
   └────────────────────────────────────────────────────┘

STRIDE Threat Categories

Category Description Security Property Countermeasures
Spoofing Pretending to be someone/something else Authentication MFA, certificates, tokens
Tampering Modifying data or code Integrity Signing, hashing, access controls
Repudiation Denying an action occurred Non-repudiation Audit logs, digital signatures
Info Disclosure Exposing information Confidentiality Encryption, access controls
Denial of Service Making system unavailable Availability Rate limiting, scaling, filtering
Elevation of Privilege Gaining unauthorized access Authorization Least privilege, input validation

Threat Modeling Methodologies

STRIDE

Microsoft's threat categorization. Systematic, developer-friendly. Best for: Application threat modeling.

PASTA

Process for Attack Simulation and Threat Analysis. Risk-centric, 7-stage process. Best for: Business-aligned risk.

Attack Trees

Hierarchical diagram of attack goals and methods. Visual, intuitive. Best for: Specific attack scenarios.

LINDDUN

Privacy-focused threat modeling. Linkability, Identifiability, etc. Best for: Privacy-sensitive systems.

Threat Modeling Best Practices

Threat Modeling Guidelines

1. Start Early: Threat model during design, not after development. Changes are cheap here.

2. Include Developers: They know the system best. Security facilitates, developers participate.

3. Keep It Updated: Threat models are living documents. Update when architecture changes.

4. Focus on Trust Boundaries: Most threats occur where trust levels change. Prioritize these.

5. Don't Boil the Ocean: Time-box sessions. 60-90 minutes per component is often enough.

6. Document Assumptions: Record what's assumed secure. Validate assumptions later.
